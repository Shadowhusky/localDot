# From request to verified software

Use this for a feature, integration or substantial fix. A one-line change does not need a document or ceremony.

1. **Frame the result.** Turn the request into a short list of observable outcomes. Name existing behavior that must remain. Inspect the actual project, data paths, runtime versions and nearest working example before selecting an architecture. For an ambiguous choice, investigate first; ask only for a decision that materially changes the product.
2. **Find the risky boundary.** Identify the hardest assumption: authentication, streaming, data migration, third-party API, browser support or throughput. Prove that assumption with the smallest real slice before building the surrounding UI. Do not substitute mocks for the only unknown integration.
3. **Plan vertical slices.** Use the runtime's plan tool for multi-step work. Each slice reaches the user-facing result through UI/API/storage as needed. Complete one slice with realistic content and failure handling before expanding it. Update the plan when evidence changes it; planning is not a separate approval gate.
4. **Implement in the project's idiom.** Reuse its components and services. Track ownership of async work and discard stale replies; bound queues and output; make cancellation and retries explicit. Don't add a framework or generic abstraction for a single use. For React/Next.js load only relevant vercel-react-best-practices rules; use vercel-composition-patterns when the component API is the problem. Other stacks use their own official docs.
5. **Verify at the boundary.** Reproduce the original failure, test success and the most plausible failure, and exercise the actual UI. For a race, control response ordering instead of adding sleeps. For performance, compare representative before/after traces. Use engineering-quality and webapp-testing when applicable. Tests of string constants alone do not prove behavior.
6. **Review the deliverable.** Read the final diff as a maintainer: does it solve the request, preserve user data, handle failure, and avoid accidental scope? Inspect the rendered app for visual defects. Fix concrete problems, then run affected checks once more. Report evidence, remaining limits and the actual artifact/URL. Never equate an unfinished background job with a completed task.

Scale effort to risk. Reuse a known working toolchain; research only a missing capability or uncertain assumption. Do not repeatedly run the full suite after unrelated formatting changes, request reviews from multiple agents by default, or create approval gates for routine implementation. A reasonable first draft plus a focused correction pass is better than endless planning or blind patching.
