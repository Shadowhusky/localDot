# User files on the computer

Composer attachments and file answers use the same authenticated, resumable transfer. These are complete working files on the virtual computer, not documents loaded into model context. The shared instructions tell every harness to use shell tools for datasets, archives and binary files, inspecting bounded samples first. Uploading alone never extracts or executes a file.

## Transfer and ownership

- Up to 10 GiB per file, 16 attachments per draft, 20 GiB of unfinished uploads per installation. Host free space is checked before admission. Output downloads and uploads from the agent to external websites retain their separate limits.
- `POST /api/cells/:cellId/uploads` creates an idempotent UUID transfer; `GET /:uploadId` returns its acknowledged offset and final receipt. `PATCH /:uploadId` carries at most 4 MiB, an exact `Upload-Offset` and SHA-256 `Upload-Checksum`. Incorrect offsets or checksums cannot advance the upload.
- Chunks are staged in the daemon's private `user-uploads` directory. Data is synced before the offset receipt is atomically persisted. A process interruption can leave an unacknowledged tail, which the next chunk truncates. The next new upload removes records and partial data older than 24 hours. Explicit removal discards unfinished staging; completed computer files are never deleted by removing a chip.
- Completion is asynchronous. The daemon streams a whole-file checksum, then streams the file to the computer with byte-count and checksum verification before atomic no-replace publication. Both stream queues and HTTP bodies are bounded in bytes. The final path is `~/Downloads/Uploads/<upload-id>/<original-name>`; same-named attachments do not overwrite each other.
- A lost desktop acknowledgement is recovered by verifying the existing destination against the expected size and checksum. If the file changed, replacement is refused. A small completion receipt remains after staged data is removed. Paused or unavailable computers retain the transfer for retry; an older desktop helper reports that a computer update is required.
- User-initiated transfer is independent of model turns, manual control and task-feed freshness. Final placement still acquires the computer lifecycle's transfer lease: shutdown, reset and update abort/drain it. No browser focus event cancels a running transfer. Page suspension or offline events retain the selected File and upload ID in the open draft, and resume checks the server's saved offset. Full page reloads cannot restore a browser File object: select the source again; old incomplete staging expires. This limitation is not presented as successful upload.
- The UI shows acknowledged-byte progress, then “Saving to computer”, and only enables attachment submission after an exact completion receipt. Each request has its own deadline; there is no two-minute deadline for the entire dataset. Transient errors receive bounded retries with offset reconciliation; persistent problems expose Retry instead of an unresolvable “Unconfirmed” state.

The design follows the offset/checksum/reconciliation principles in the [tus resumable upload protocol](https://tus.io/protocols/resumable-upload). The endpoints are localDot's own authenticated protocol, not a claim of tus wire compatibility. The legacy single-request endpoint remains for older clients.

## Verification

The assembled regression uses the actual frontend transport, daemon routes/store, desktop client and desktop file routes. It transfers a 128 MiB binary file; simulates lost chunk and completion replies, process restart and an unacknowledged tail; and verifies hashes, empty files, same-named files, owner isolation, corruption rejection and preservation of a destination modified after upload. UI regressions cover hidden tabs, freshness changes, page suspension/resume, cancellation of one queued file and explicit retry with the same upload ID. A virtual-time regression takes three minutes to upload without hitting an overall two-minute timeout.
